# モデル旅程3000件 設計ドキュメント

> 作成: 2026-05-30
> 目的: 国内外の人気旅先を網羅したモデルプラン 3000 件を作成し、ユーザーが参照・コピーして自分の旅行に活用できるようにする

## 背景・目的
- 現状はゼロから AI で生成するか、自分の URL を貼って生成するか。「他人の事例を真似てカスタマイズする」体験がない
- 国内外のユーザーが対象。多くの目的地・日数・出発地・テーマで「すぐ使えるテンプレ」を用意したい
- Gemini API 課金枠を消費せずに、自前カタログから決定的に生成する

## ゴール（成功条件）
1. 国内外の人気目的地を網羅した約 3000 件の旅程が Supabase に投入されている
2. ユーザーは新ルート `/models` で軽量リストを見て、目的地・日数・テーマで絞り込める
3. リストの行をクリックすると既存の `/trips/[share_id]` カレンダーページが開く
4. `/explore` には混入させず、ユーザー作成プランと完全に分けて表示できる
5. 移動手段（飛行機 / 新幹線 / 電車 / レンタカー / 徒歩）が出発地・目的地・日程と整合する

## 非ゴール（やらないこと）
- Gemini API を3000回呼ぶ（コスト上不可）
- 海外用の現地予約導線（Phase 6 のアフィリエイトで別途）
- 旅程ごとに完璧な店名カバー率を出す（80点ベース、ユーザーがカスタマイズ前提）
- パッケージツアー由来の団体バス・添乗員前提行程

## アーキテクチャ

### データ保存
- 既存 `trips` テーブルを再利用。`is_official BOOLEAN DEFAULT FALSE` を追加
- 旅程 JSON 構造は既存 `Itinerary` 型を完全踏襲（Gemini が吐く JSON 仕様準拠）
- `edit_token = NULL` で投入（既存コードの「レガシー後方互換: 誰でも編集可」扱い）
- `/explore` クエリに `is_official = false` フィルタを追加

### 生成パイプライン
```

```

### 1目的地あたりのカタログ
```ts
type Destination = {
  id: string
  name: string                       // '京都'
  emoji: string
  region: RegionId                   // 移動時間判定に使う
  country?: string                   // '日本' / '韓国' …
  trip_style: TripStyle              // 'public_transit' / 'rental_car' / …
  intra_transport: TransportMode     // スポット間の典型移動
  spots: SpotEntry[]                 // 20〜40
  hotels: HotelEntry[]               // 3〜8
  area_clusters: AreaCluster[]       // 同日にまとめるべき地理クラスタ
  default_themes: Theme[]            // 推奨テーマ
}

type SpotEntry = {
  id: string
  name: string
  description: string                // 一文（30〜80字）
  type: SpotType                     // 観光/グルメ/その他
  duration_minutes: number
  address: string                    // 区＋町
  area: string                       // クラスタID
  themes: Theme[]                    // 適合テーマ
  popularity: number                 // 1-5
  needs_booking?: boolean
}
```

### Variant 展開ルール（合計 ~3000 件）

国内:
- 目的地 35 × 日数 [2,3,4,5] × テーマ [観光/グルメ/絶景/温泉/カップル/家族/歴史] × 出発地 [東京/大阪/名古屋/福岡] のうち、地理的に意味のある組み合わせのみ
- 重複排除と人気度バランスで ~1800 件

海外:
- 目的地 30 × 日数 [3,4,5,6,7] × テーマ [観光/グルメ/絶景/ショッピング/ビーチ/夜景] × 出発地 [東京/大阪] のうち成立する組み合わせ
- ~1000 件

欧州周遊:
- 10 ルート × 日数 [6,7,8,9,10] × テーマ [観光/グルメ/世界遺産/アート] × 出発地 [東京/大阪]
- ~200 件

### 旅程組み立てロジック

1. **trip_style 決定**: Destination の `trip_style` を採用
2. **1日目スポット数**: 出発地→目的地の移動を考慮（既存 `getDepartureTravelHint` を spot-count に変換）
   - 国際線: 1〜2 件（夕食のみ）
   - 国内離島・北海道: 3 件まで・午後開始
   - 長距離新幹線(4h+): 3 件まで・13時開始
   - 中距離(2-4h): 4 件まで・11時開始
   - 近距離: 4〜5 件・9時開始
3. **中日**: 4〜5 件、9時開始
4. **最終日**: 帰路移動を考慮（同様にスポット数制限）
5. **同日内**: 同一 `area_cluster` のスポットを優先（地理的整合性）
6. **テーマフィルタ**: `spot.themes` がテーマに合致するもの優先、足りなければ汎用観光で補完
7. **時刻配置**: `time-scheduler` で「前spot.time + duration_minutes + 移動目安gap」を加算
8. **重複排除**: 旅程内で同一スポット名禁止（既存 `sanitizeItinerary` と同じ）
9. **宿泊**: 各中日終了後にホテルカタログからエリア整合する 1 軒
10. **sidebar_spots**: 配置しなかった上位 8 件を追加

### 整合性チェック
- `sanitizeItinerary` を通して時刻逆転・重複を最終補正
- 1日のスポット合計時間が 12 時間を超えないこと

### DB 投入
- `@supabase/supabase-js` の service_role キーで bulk insert
- 1000 件ずつ 3 バッチに分割
- 投入前に `is_official = true` の既存レコードを全削除（idempotent）

## エラーハンドリング
- カタログ生成時の validation エラーは throw → スクリプト終了
- DB 投入失敗は再試行 1 回、それでも失敗ならスキップしてログ出力
- 投入後の件数を確認し、目標 3000 件との差をレポート

## テスト計画（時間制約のため簡易）
- ジェネレータ単体: 10 件サンプル生成 → JSON 構造が `Itinerary` 型に適合するか目視確認
- 投入後 `/models` で表示確認、ランダム 3 件を `/trips/[share_id]` で開いて移動整合性を確認

## 影響範囲
- DB: `trips` テーブルに 1 カラム追加（既存データに影響なし）
- 既存 API: `/explore` のクエリのみ変更
- 新規: `/models` ルート・カタログモジュール・生成スクリプト

## ロールアウト
1. ローカルでスクリプト実行 → Supabase 本番に直接投入（service_role）
2. UI を git push → Vercel 自動デプロイ
3. 動作確認後、PRODUCT_NOTES.md に Phase 3 「モデルプラン投入完了」として追記

## リスク
- 3 時間内の品質確保: 35＋30＋10 = 75 目的地分のカタログを書き切る必要がある。スポット最小数（10件/目的地）でも 750 spots 必要 → カタログは効率重視で「広く薄く」
- Supabase free tier 容量: 3000 件 × 平均 10KB = 30MB → 500MB 枠の 6%、問題なし
- レガシー編集権限: edit_token=NULL のため誰でも編集可能だが、ユーザーは「コピーして使う」が主導線なので影響軽微
